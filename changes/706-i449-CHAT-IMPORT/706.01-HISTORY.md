## The defect: large answers were sometimes cut short

- **What happened:** when the chat server sent an answer bigger than about 8 KB over your private socket, it closed the connection before all of it had been delivered, roughly one time in six. `doz chat read` on a long room would fail, and the peer's full-screen client could show a long room oddly.
- **Where it could bite tonight:** an agent collecting a large message, or downloading a file, over the network port. The buffers there are larger, so it would be rarer, but it's the same flaw.
- **The fix:** the server now waits until the answer has actually been delivered before closing.
- **Proof:** 120 answers of 25.7 KB over the socket all arrived whole, where 7 of 30 were cut before. 40 reads of a long room in a row all succeeded. A new test keeps it that way.
- **This shipped in 0.51.4.** It's in 0.51.5 from the start.

## Import (706): implemented, green on its own checks

- **What it does:** a dry run prints exactly what would come in and which participants must be added first, with the commands. The real import then brings in rooms, messages and attachments.
- **Tested against a copy built by the switchboard's own script.** After importing, turning chat on wakes nobody: no webhook calls, nothing for a poller to collect, no new lines in rooms.
