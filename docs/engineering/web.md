## The web layer (`doz ui`)

- **ONE dashboard command** (645, owner: "merge `doz ui` and `doz serve`"). Without its LAN option (`ui.lan`, default
  OFF) `doz ui` is **loopback only, nothing else representable** (`WebLoopbackAddress`: 127.0.0.1 and a port) — no
  flag, variable or setting but the LAN option binds another address. The LAN option (`doz ui --lan`, below) binds
  the LAN profile in the SAME process on the SAME port; it is built only by `LANDashboard` in `ServeCommand.swift`
  (`DozableWebServer.bindServe`, `WebServeState`) — the audit keeps it out of `UICommand.swift` (the browser
  opener). The PORT is the ONE setting `ui.port` (`doz ui start --port N`, `$DOZ_UI_PORT`; `WebDashboardPort`):
  `0` (the default) = without the LAN the reuse — the port this store's LAST UI had (`<store>/ui.port`), asked for
  again when nothing listens there (`WebLoopbackAddress(reusing:)`: ≥ 1024), else the OS picks and `doz ui` SAYS
  so (naming the holder, `PortHolder`: `/usr/sbin/lsof`, read-only); with the LAN `serve.port` (7443 — the earlier
  `doz serve`'s, so its devices' origins keep working), fixed. Or a fixed port 1024–65535, never silently swapped
  (taken → `doz ui` refuses, naming the holder; `bind(fixedPort:)` has no OS fallback). The port is no secret and
  grants nothing — an installed dashboard app belongs to one, which is why it may be fixed.
- **Who asks is decided per REQUEST** (`DozableWebServer.requestContext`): without the LAN option every request is
  the Mac's (`.mac`); with it, the Mac's own browser ONLY when `WebServeRules.isMacRequest` — the connection's peer
  AND local address loopback, Host exactly `127.0.0.1:<port>`, and no forwarding header (`Forwarded`,
  `X-Forwarded-*`, `X-Real-IP`: a reverse proxy on this Mac connects from loopback too). Anything else is a remote
  device (`.remote`) under the LAN rules below. The accept gate runs BEFORE this (a sandbox is dropped first).
  `WebAuth` is ONE sign-in model: the Mac's sessions (the link, `doz_ui_<port>`) and, with the LAN, the devices
  (`doz_serve_<port>`); each request is authenticated against its principal's store ONLY — a cookie value of one
  never signs a request of the other in, whatever name it is presented under (`ServeHTTPTests`).
- **Every request: exact `Host` first** (`127.0.0.1:<port>`, the DNS-rebinding defence), then the
  closed route table, then the session. `Origin`, when present, must be exact (required on every
  unsafe method); `Sec-Fetch-Site` other than `same-origin`/`none` is refused. No response carries
  `Access-Control-Allow-*`, ever; no response reflects a request value.
- **The link's capability lives only in a URL FRAGMENT**, is exchanged ONCE (`POST /api/v1/session`,
  `Authorization: Bearer`) for an HttpOnly `SameSite=Strict` cookie named for the port, plus a CSRF
  token the page keeps in memory and sends as `X-Doz-CSRF` on every unsafe request. It never
  enters a log, a file, an event, a JSON field or a process argument — the browser is opened through
  LaunchServices (`LSOpenCFURLRef`), never `/usr/bin/open URL`; `--print-url` prints only to a TTY.
  `WebBootstrapCapability`'s description and mirror are redacted (a struct's default description
  prints its fields — DeckStack's never-conformed version still printed through `"\(cap)"`).
- **Typed routes only.** A new capability is a new `WebRoute` case and a typed `DozableWebData`
  method. Never a generic command, exec, file-read, URL-open, proxy or PTY route.
- **Actions (phase 2) are `WebAction`: a closed enum, decoded STRICTLY** (unknown action or field,
  wrong type, out-of-rule value → 400 with a fixed message that never echoes the value), each
  **exactly one `HostOp`** the CLI also sends — the web layer adds no daemon operation.
  `WebActionTests.testEveryActionIsExactlyOneAllowedHostOp` pins the set; `exec`, `attach`, `key-set`,
  `account-add` and `host-stop` are never reachable AS AN ACTION (591: `attach` is reachable only
  through the ticketed terminal socket below; `host-stop` only inside `daemon-restart`, which
  `HostWebData.restartHost` refuses only when no daemon runs — 647, owner: the status card restarts any running daemon; 594
  W20 offered it only for an OLDER one). Destructive ones (reset, rm,
  point revert/rm, image rm, account rm) carry `confirm` equal to the name. Shutdown keeps the disk,
  so it carries no `confirm`: the page asks with a plain dialog that can stop asking
  (the setting `ui.confirm_shutdown`, doz.toml — no longer localStorage). 617 (owner: "same simplified delete
  experience"): the page confirms every destructive one with ONE component, a box to tick (`confirmAction` /
  `confirmWithCheck`, `components/dialog.js`: "Yes, reset demo") — never a name to type; the request still carries
  `confirm`. **No secret is ever an
  action's input** (590's D3). Since 594 an ACCOUNT's key or token may be typed in a
  masked field — through the one typed route `POST /api/v1/accounts`, never an action, while
  `ui.allow_secret_entry` (see the 594 section); and a sandbox's own key through `POST
  /api/v1/sandboxes/NAME/key`.
- **An action is an operation**: 202 at once, the daemon call in `WebOperations` (beyond its lane's width it is
  QUEUED, never refused — below), its progress and outcome as SSE `op` events. The outcome is a line written from
  the result — never the result passed through.
- **The lifecycle queue** (650, owner: All sandboxes woke 12 at once, each slow from the contention, and past 8 the rest
  were refused). Two lanes in `WebOperations`, each FIFO: start / wake / resume / sleep / hibernate / shutdown run at most
  `ui.batch_concurrency` (1–8, default 3, read whenever a place frees) at once; every other action at most 8; a `pause`
  and a resume of a sandbox the monitor last saw PAUSED (`WebOperations.lane`: the overview's phase, cached in
  `reconcile`; the terminal's keystroke wake passes the phase it knows; unknown → the lane, the safe side) never wait.
  A queued operation is `state: "running"` (the page reads running as "under way" in ~40 places) with `queued: true` and
  `position` (1-based in its lane), its text "queued — N ahead" / "queued — next"; every move is an `op` event; at its
  turn `queued` is cleared and `startedAt` reset. A person's own request (anything but the page's bulk controls, which
  send the envelope field `batch: true` — `WebAction.decodeRequest`; `decode` still refuses it) goes ahead of every batch
  one, and a person's repeat of a QUEUED batch operation moves that one ahead (the same id); any other repeat is still
  409. Refused (503 `too-many-operations`) only past `WebOperations.maxQueued` (256) waiting. `POST
  /api/v1/operations/cancel` (a typed route, not a `WebAction` — it sends no HostOp; CSRF; strict `{ids}` 1–256; the
  same `WebExposure` decision as actions) withdraws QUEUED ones only → `{cancelled, notQueued}`; a cancelled one ends
  `interrupted` "cancelled before its turn — nothing was done". The ring forgets only ENDED operations beyond 50; a
  queued one read back after a `doz ui` restart was never sent: it ends `interrupted` "doz ui restarted before its turn
  — it was not started" and `reconcile` never resolves it. The daemon and the CLI are unchanged (a request already sent
  cannot be withdrawn). The page: the waiting mark is `QUEUED_GLYPH` (`hourglass`: the vendored Lucide set has no
  clock), the pill "Queued", the status line + Cancel (`paintRowOps`), the start panel's waiting state, Operations' row
  + Cancel, the bulk bar's "N queued · Cancel all", the nav's mark. `WebOperationsQueueTests`, `WebActionHTTPTests`.
- **Open in Terminal** writes a one-shot `.command` file (0700, in a 0700 per-user directory; it
  runs `rm -f -- "$0"` then `exec '<doz>' attach NAME [SESSION] --store '<store>'`, names
  allowlisted, paths quoted) and `open`s it, so the user's DEFAULT app for `.command` files runs it
  (Terminal, iTerm2, Ghostty). No AppleScript, so no Automation permission and no second window
  (the AppleScript version opened two when Terminal was not running). Never a command from the browser.
- **End / Restart session (`SessionRestart.swift`)**: daemon ops `session-end` / `session-restart`, held under
  the SAME `sessionGate` as `open-session`, RUNNING sandboxes only (never a wake). Ending is
  `GuestCommand.endSession` (root): the session's tmux server (`/tmp/tmux-*/doz-NAME`) killed first, then
  HUP → TERM → KILL of the program's PROCESS GROUP (forkpty made it a leader), done when deckhold's socket is
  gone (`doz-end hangup|terminate|kill|not-running|stuck`). A restart reopens through `openSessionLocked` from
  `<sandbox>/sessions.json` (`SessionRecords`: argv as CHOSEN — before pi's prompt file, tmux and a resume —
  workdir, user, variable NAMES only; ≤ 64; 0600; cleared with the sessions: shutdown, reset, died-with-host;
  fields only ever added). No record: the default session's argv, else refused. 648 (owner: "do for all"): EVERY
  session running the agent's own program (argv == the default) first gets its OWN conversation where the agent records
  which process holds which — Claude Code's `~/.claude/sessions/<pid>.json` `sessionId`, read before the program ends
  (`SessionResume.exactCheck`: only with a transcript in `~/.claude/projects/*/<id>.jsonl`; `exactArguments`: a UUID
  only) → `--resume <id>`. Otherwise the default session of an agent image gets `SessionResume.arguments` as
  `extraArguments` (never recorded): Claude Code
  `--continue` (only after `SessionResume.check` finds ~/.claude/projects/<cwd, non-alnum→'-'>/*.jsonl — it
  refuses without one), Codex `resume --last` (0.160.1: newest in the cwd, else a new one; `--all` would ignore
  the folder), pi `--continue` (newest else new); `fresh` = none. CLI `doz sessions end|restart NAME SESSION`
  (`sessions` became a group whose default subcommand `ls` keeps `doz sessions NAME`; `restart` attaches afterwards
  only when stdin AND stdout are a terminal — a script's `--yes` restarted and then attached forever — never with `-d` or
  `--json`, and `--attach` forces it: `SessionsRestart.attaches`); web actions
  `session-end` / `session-restart` (one HostOp each; `components/session-actions.js`: a tab's ⋯ and
  Home's ⋯ / End… (635); a restarting pane (`t.restarting`) ignores the `ended` frame and the socket's close, shows
  "Restarting the session…", and reattaches with its scrollback when the operation is done).
- **`open-session` is serialized per sandbox** (`HostCore.sessionGate`, a `KeyedGate` held across
  its awaits — the actor alone is re-entrant) and idempotent: a concurrent or repeated open of one
  session answers "already running", and a deckhold "Address in use" re-lists and answers with the
  session that won. (590: two clicks during a first boot started two `deckhold serve`s.)
  `KeyedGateTests`, and `test-cli`'s "concurrent opens of one session".
- **A cold start is JOINED, never raced** (610, 590.B3: an open during a first start's image preparation ran while the
  sandbox was still OFF and failed "… is off"). `HostCore.coldStarts` (`ColdStarts`, a lock like `KeyedGate`) holds a
  sandbox from the moment `start` decides to boot it from off/failed — its preparation included — to the boot's end.
  `ensureRunning` (open-session, attach with wake, exec/run) waits for it and then looks again (a fresh `get`: a
  Dockerfile sandbox is re-adopted mid-start); `open-session` joins it BEFORE queueing at `sessionGate`, so every open
  made during it ends with the start; a second `start` joins the first. A failed start fails every joiner with
  "NAME did not start — <the start's reason>". With no start under way an off sandbox is refused as before (nothing
  starts unless asked). `ColdStartJoinTests` (no VM: a gated preparation); `probes/590-*/browser-repro-open-during-boot.mjs`
  (a real claude-code first start, two opens during it: both wait, one session).
- **A poller never counts sessions**: `ls` with `withSessions: false`. Counting runs `deckhold ls`,
  which connects to every session's holder — each connect is a line in the guest's
  `/run/deckhold/NAME.log` (tmpfs); the UI's 3 s poll grew one by 600 KB in 9 hours. A repeat of an
  in-flight action (same `WebAction.dedupeKey`) is 409.
- **The overview's sessions are the daemon's registry, never the guest's** (635, `SessionRegistry.swift`,
  `HostCore+Sessions.swift`): `SandboxInfo.sessionList` / `sessionMore` (name, program's basename, `isDefault`,
  `openedAt`, `saved` — never a command line, nothing that moves by itself: the overview is compared poll to poll for
  `changed`). Fed by the daemon's own events — `openSessionLocked` (`opened`: a new epoch; "already running": `seen`), an
  attach (`seen`), the status watcher's `.ended` ONLY for the epoch it was opened under (a restart's late `.ended` of the
  old program re-watches instead), `session-end` — and reconciled from every guest list the daemon makes ANYWAY
  (`refreshStatusWatches` per transition, `detail`, `sessions`, the open path, the periodic capture's
  `ScreenCaptureReport.listed`), never dropping an entry registered after the list began (`mark`). Running → memory
  (the saved screens until this run's first list); paused/asleep/hibernated → the saved screens (`saved: true`);
  off/failed/booting → none; cleared on off and `rm`. **Staleness is accepted, never a new guest call**: a program that
  exits with nobody watching (a holder older than 612, or a watcher that gave up) or a session started inside the guest
  is corrected at the next list the daemon makes anyway — at once for the page's own sandbox, else within
  `daemon.screen_capture_minutes`. `SessionRegistryTests`; `make test-cli-sessions` checks it and that 20 overviews add
  no line to a holder's log.
- **The policy preview is the daemon's own function** (`HostCore.editedPolicy`), so the preview is
  exactly what `net-policy` applies. **Metrics CSV cells are defused** against spreadsheet formulas.
- **The UI is a CLIENT of the daemon** (daemon.sock) in its own process — it never owns a VM, and the
  the daemon (`DozableHost`) never imports `DozableWeb` (audit). Looking never starts a daemon (the CLI's rule, incl. its
  recovery exception); the daemon's event stream is followed only while a sandbox is live, so an open
  UI never keeps an idle daemon alive.
- **The API returns projections** (`WebModels.swift`), field by field — never a daemon result passed
  through. A new daemon field reaches the browser only when added there on purpose; no field may hold a
  secret (`testNoAPIModelHasASecretShapedField`).
- **The page renders with `textContent` only.** Hostnames, paths, session commands and notes come
  from inside a sandbox, which is untrusted. The asset compiler refuses `innerHTML`, inline script or
  style, event-handler attributes and external URLs — in every module. The CSP refuses inline script and eval
  (`script-src 'self'`); since the owner's ruling of 2026-11-20 it ALLOWS inline styles (`style-src 'self'
  'unsafe-inline'`), so an editor such as Monaco or CodeMirror can run in the page. That makes `textContent`
  rendering and the sanitiser the only guard against agent-written text restyling the page — hiding or faking a
  warning, a confirmation or an Ask's buttons — so keep both, and never let agent text become markup. A per-load
  nonce instead is a backlog item. The terminal frame keeps `style-src 'self'`
  (`WebInstallableTests.testScriptsStayStrictWhileStylesMayBeInline`).
- **The page script is native ES modules, layered** (v1: no framework, no bundler; that is v2). `index.html`
  loads `<script type="module" src="/app.js">` (the CSP's `script-src 'self'` covers modules). Layers:
  `dom` < `core` < `components` < `views` < `app.js` — a module imports only from its own layer or below
  (components never import a view; core never imports a component or a view), never in a cycle. A call UP the
  layers (the router dispatching to its views, an operation's end re-rendering, the SSE handler) is
  `const name = upcall('name')` at the top of the lower module, and `app.js` provides every one with
  `provide({…})` before anything runs (`core/hooks.js`); only functions go up — a VALUE a lower layer needs moves
  down (the terminals' data is `core/terminals.js`, the wizard's steps `core/wizards.js`). The single `state`
  object is ONE export of `core/state.js`, mutated in place (an import binding cannot be assigned: a top-level
  `let` stays in the module that assigns it). The compiler (`Scripts/build-web-assets.swift`) CHECKS the graph:
  relative specifiers only (`./x.js`, `../core/x.js`), a module that exists, no dynamic `import()` (but the ONE the compiler's
  lazy-import table admits — "Vendoring by peer commit" below), the layers, no
  cycle, no module the entry does not reach, every `upcall('x')` provided and nothing provided that nobody
  upcalls. It hashes bottom-up — each module's specifiers rewritten to its dependencies' hashed names, then the
  module hashed (`/assets/app/<layer>/<name>-<sha16>.js`, immutable, in the manifest; the route table admits
  exactly `/assets/app/<layer>/<file>`) — so `app-<sha16>.js` changes whenever any module does and `hello.script`
  still names "this build's page". `WebModulesTests` checks what ships and the compiler's refusals. JSDoc
  `@typedef`s document the shared components' parameters (`btn`, `callout`, `dialog`, `menuButton`/`moreMenu`,
  `renderAccessStep`); there is no `tsc` check (no pinned TypeScript without an npm install).
- **The probes' names**: the one script's top-level names were globals and the workspace's browser probes
  read and call some (`state`, `terminals`, `sview`, `act`, `saveSetting`, `gridRefresh` …). `app.js`'s
  `expose({…})` keeps exactly those reachable by name (one a lower layer upcalls is its hook — so a probe that
  wraps it, 594 host-watch's `gridRefresh`, wraps what the page calls). Nothing in the page uses them; a probe
  that needs another name adds it there. A probe cannot wrap a function a module calls internally (593
  boot-progress wrapped `toFrame` — it would need its capture moved into the frame).
- **The split was a MOVE**: `probes/607-*/split-app.mjs` cut the 0.28.0 `app.js` into its top-level
  statements and wrote each, byte for byte, into the module `map.mjs` names; `verify-move.mjs` proves every
  statement and comment line is kept exactly once. New code goes into the module of its area; a new module is a

## Chat

The Chat page (`#/chat`, `#/chat/ROOM`) — the chat server's rooms for the person (chat.md, "In the dashboard"). Its room
surface is the ONE chat client: a workspace's page shows the same subtree, moved (`mountChat`, below "A workspace's page").

- **Routes: a CLOSED set under `/api/v1/chat/`** (`WebRoute.chat(WebChatRoute)`, `WebChat.swift`), each a fixed call on the
  owner's socket built from checked values — never a proxy. GET `status` (no upstream: `chat.enabled`, the daemon's lock and
  `supervisor.json` → `off | no-daemon | starting | running | failing`); GET `state` (`/api/state` PROJECTED: rooms, archived,
  participants {name, kind}, default_room, reactions, version — `token_service`, `need_token`, `https_url`, `apps`,
  `release` dropped); GET `presence`, `unread?ROOM=SEQ…` (≤ 256), `protocol`, `rooms/ROOM/messages?after&before&limit`
  (`X-More` copied back — the only upstream header that ever is); POST `rooms/ROOM/messages` (CSRF and the unsafe-request
  checks; a strict body `{content ≤ 64 KiB, to? ≤ 32 names, re_msg_id?}` re-encoded; 80 KiB — `bodyLimit(for:)`, every other
  route keeps 16 KiB); GET `stream`; GET `files/ID/NAME` (the one path whose name may carry `%20`, parsed before the
  route table's no-`%` rule). Acting (every one a POST with the unsafe-request checks): `rooms/ROOM/reactions` (`{msg_id,
  reaction}`, a reaction 1–32 bytes, no control character), `rooms/ROOM/messages/ID/edit` (`{text}` ≤ 64 KiB, 80 KiB),
  `…/ID/delete`, `…/ID/reveal` and `typing` (no body or `{}`; upstream always `{}`), `files?name=NAME` (the upload, below);
  the post also takes `attachments: [{id}]` (≤ 10; with one the text may be empty). **`X-Chat-Id`** is REQUIRED on a
  reaction, an edit and a delete (`takesActionID`: the chat server does each once per id), passed upstream only as a
  lower-case v4 UUID (else 400) — the ONLY header of the browser's that ever reaches the socket. Rules: a room or a name
  `^[a-z0-9][a-z0-9_-]{0,63}$`, a message id lower-case hex and `-` ≤ 36, a file id 16 or 32 lower-case hex, a file name
  `[A-Za-z0-9._ ()+-]` ≤ 120 bytes not starting with a dot or a space (in the upload's query: `%XX` decoded, a raw `+`
  refused, re-encoded upstream byte by byte); a query only where a route takes one. Never reachable: `/agent/*`,
  `/api/reload`, room apps — anything not listed. Nothing else of the browser's request (path, query, cookies, Origin,
  other headers) reaches the socket.
- **The upload** (`.upload`) is decided from the request's HEAD before a byte of its body is read
  (`DozableWebServer.uploadPreflight`, called by `serve()` for that route only): exact Host and Origin (required), Fetch
  Metadata, the session and its CSRF token, who may (`serve.chat`), `Content-Type: application/octet-stream` exactly (never
  a form), and a declared size over the chat server's 20 MiB (`WebChatProxy.maximumUpload` = `ChatProtocol.maxFileSize`,
  pinned by a test) — each refused at once and the connection closed. The read stops one byte past the limit
  (`bodyLimit`: 20 MiB + 1; chunked included) → 413 `chat-file-too-large`. The answer is projected (`uploaded`: id, name,
  type, size, url — never the server's `path`, a folder of this Mac).
- **Answers**: JSON as `application/json`; the message, presence, unread and protocol bodies pass through (the protocol's
  view for the person; its human API has no token field) only when they ARE JSON of the expected kind; an upstream refusal is
  re-wrapped `{error:{code:"chat", message}}` (≤ 300 characters); no socket → 503 `chat-off` (naming `doz chat on`) or
  `chat-not-ready` (naming `doz chat status`). Calls run on their own queue, at most 8 at once — never the event loop.
- **Attachments** are served from this origin with headers decided here from the upstream type alone: PNG, JPEG, GIF, WebP
  inline; anything else `application/octet-stream` + `Content-Disposition: attachment`; always `nosniff`,
  `Content-Security-Policy: sandbox; default-src 'none'`, CORP same-origin, `Cache-Control: private, no-store`, no referrer.
  HTML and SVG never render as the dashboard. At most 21 MiB.
- **The stream** is its own (`chatHub`: 4 at most, the bounded queue) — never the page's main stream, so an open dashboard
  never makes the person "here". One upstream per browser stream, followed by a thread (`WebChatProxy.relay`); each `data:`
  line must be a JSON object with a string `kind`, ≤ 1 MiB, and becomes `event: chat`; an upstream `resync` ends the client
  with `resync`, an upstream end with `end {reason: chat-gone}`. The client's end — the browser gone (a 2 s heartbeat finds it),
  signed out, rotated, too slow — cancels the upstream (`StreamHandle`: `shutdown`), so the server marks the person away.
- **Exposure**: `WebExposure` kind `chat`, decided for a remote (LAN) browser by **`serve.chat`** (`off | read | write`,

  every route, before its session is looked at (the sidebar's entry stays hidden: its status is refused); `read` → the reads,
  and 403 `chat-read-only` on every route that is not `isSafe` (post, upload, react, edit, delete, reveal, typing);
  `write` → everything. `chat/status` carries `access: read | write` so the page disables its composer and offers no
  control that changes anything. Through these routes a browser acts as the person — the verified human, whose words the
  agents act on — which is why the default is off: a device's cookie lasts long, and a lost phone could instruct every
  agent. Every remote write is ONE line in the serve audit log (`auditChange`, kind `change`, route `chat-<call>` from

## Browser terminals

- **A terminal is two steps.** `POST …/terminal-ticket` (CSRF, strict body) mints a 256-bit ticket that
  works ONCE within 30 s, bound to the browser session's cookie, the sandbox, the session and the mode
  (`WebTerminalTicketStore`); `GET …/terminal-socket` upgrades only with exact Host, Origin REQUIRED,
  Fetch Metadata, the cookie and exactly one `doz-ticket.<t>` in `Sec-WebSocket-Protocol` (never the
  URL; the answer echoes only `doz-terminal.v1`). A ticket presented wrongly is spent.
- **NIO's typed upgrader drops a refused request's head** (only what followed it reaches the HTTP
  channel): a refusal is stashed by `shouldUpgrade` and answered from there (`UpgradeGate`), with
  `Connection: close`. `WebTerminalHTTPTests.testTheUpgradeRefuses…` hangs if that regresses.
- **The bridge adds no HostOp**: it sends the CLI's `attach` with `wake: false` (a watcher: size 0×0 =
  keep the session's size), relays PULLED reads (backpressure — no queue grows), strips `0xFF` from
  input (the attach wire's frame byte), turns the daemon's end notice into an `ended` frame (never on
  screen — `holdBack` covers the `ESC[0m` in front), and reattaches across a hibernation.
- **The viewer a person types in owns the session's size**: a session has ONE size and the last viewer
  to send one set it; `doz attach` from a terminal of another size left a web pane showing a TUI drawn for the
  other width (stray text, stale glyphs where it draws blanks) until the pane's own size changed. The relay
  (`HostServer`'s attach, `HostCore.sizeOwners`, `SessionSizeOwners`) re-applies a viewer's size before its
  keys when another viewer sized the session since (a watcher's 0×0 never owns it). 609's residue — deckhold's snapshot after a narrowing reflow
  dropped an EMPTY soft-wrapped row, so a TUI's prompt sat a row off on that viewer — is fixed in deckhold (below).
- **deckhold's SNAPSHOT is placed run by run**: libghostty-vt's formatter, unwrapping, counts a line's newline only at
  its last row, but counts an EMPTY row (no text) as blank before that — a wrap into or out of an empty row lost a
  newline and every row below landed one high on the viewer. `send_snapshot` now formats the active area in runs (a row
  with text and the rows with text it soft-wraps into; a run also ends at an orphaned spacer head, and stops its
  selection before it), each after a CUP to its own row; the modes go with the first run, every other extra with the
  last. `make deckhold-snapshot-check` (`Guest/deckhold/test/`: deckhold.c itself against a Mac build of the SAME
  ghostty commit) replays every snapshot on a fresh emulator and compares cell by cell (fixed cases + a seeded fuzz of
  screens × size changes; 0.30.1's source failed ~45 %). Run it on any change to `send_snapshot` or the ghostty pin.
  648: the formatter writes NO blank cell that carries only a background (tty-clock's digits, a status bar's padding — a
  new viewer showed gaps until the program redrew), and leaves a coloured blank's background on the plain blanks after
  it, past the edge into a wrapped continuation. `paint_blank_backgrounds` repaints, after the runs and inside
  DECSC/DECRC (insert and origin mode off meanwhile), every blank of a row holding a coloured blank and of its wrapped
  continuations — as SPACES, never ECH (ghostty's erase resets the row's soft-wrap). The check compares each blank's
  background too (`blank_cell_bg`, deckhold's own reading) and its fuzz paints with backgrounds.
- **GRID only to a holder that ANNOUNCED it** (648, painted thumbnails). deckhold's `'G'` GRID `{gen u32}` is answered
  with the screen as cells (binary, WIRE in deckhold.c: version, gen, changed 0/1/2, then cols, rows, cursor, default
  colours and per row runs of `col, cells, flags, fg?, bg?, text`) built from libghostty-vt's RENDER STATE (one in `S`,
  updated only when asked — never on the output path). `S.gen` starts at 1, never wraps to 0, moves with every read of
  the program's output and every resize; an asked gen of 0 always gets the grid. An OLDER holder (a session started
  before an update keeps its binary) DROPS a client on an unknown frame — on the status watcher that would end the
  session's status — so a holder that knows GRID says so: its WATCH answer (the first `'T'`) starts with `grid=1`
  (`SessionConnection.gridCapable`; an older daemon's STATUS parser ignores the field) and its `ls` INFO line carries
  `grid=1` before the status and the command (`SessionInfo.grid` — the capture's check). `requestGrid` refuses
  without it. The daemon op **`session-grids`** (`HostCore+Grids`, read-only: in-process every item is `no-host`): ≤ 64
  `{sandbox, session, gen}` across any sandboxes, ONE GRID frame each on the status watcher the daemon already holds —
  no new guest exec, no attach, no viewer — RUNNING sandboxes only (never a wake), ≤ 2 requests under way per sandbox,
  ≤ 4 outstanding frames per watcher, 1 s each; answers `grid` | `unchanged` | `unavailable` + a fixed reason, in order.
  The text is untrusted: `ScreenGrid.decode` checks every length and bound and makes it inert (C0/C1/DEL and bidi
  controls → U+FFFD; 4 KiB a row; ≤ 1000×500). The web route **`POST /api/v1/grids`** (`WebGrids.swift`: CSRF, strict
  `{items: [{sandbox, session, gen}]}`, `WebExposure` read) answers `{items: [{sandbox, session, state, grid?,
  reason?}]}` (`reason` in plain words) through a RUNNING daemon only — with none every item is unavailable, nothing is
  autostarted and nothing loaded in-process (the page polls twice a second). `make deckhold-grid-check` (every row's
  text is the holder's screen, a fuzz), `ScreenGridTests`, `SessionGridsTests`, `WebGridsTests`, `make test-cli-grids`.
- **A wake brings this build's deckhold** (`Sandbox.refreshDeckhold` in `.applyGuestFixes` — 651: after the wake is

  (`WebAssets.isFrameAsset`); every other file keeps the page's rules. A response's own header
  REPLACES a default of that name (the frame's CSP/XFO) — never a second copy.
- **The frame protocol is closed and checked on both sides** (frame.js `valid`, `components/terminal.js`
  `validFrameMessage`): source window, opaque origin, known type, exact fields, typed and capped;
  anything else is dropped and counted. Page → frame: init (mode interactive | watch | saved) / write /
  paste / focus / keep-scrollback / live (593: saved → interactive | watch only) / top (593: a Boot log
  opens at its first line) / grid (648: `{gen}`, an integer 0–2³²−1, exactly two fields, only once the engine runs).
  Frame → page: ready / opened / data / resize / title / paste / paste-too-big / failed / key (593: a
  key on a saved screen, no content) / link (636: a Cmd-clicked link's URL, ≤ 2048) / grid (648: exactly two fields —
  `same: true`, or a `grid` that passes `core/grid.js` `validGrid`: ≤ 1000 × 500, `lines` exactly `rows`, every run
  typed and inside its row, colours `#rrggbb` or null, ≤ 4096 characters of text a row; the frame makes its text inert
  and caps it before sending).
- **The frame wraps the engine** (ghostty-web 0.4.0 fails the bar alone): a link opens ONLY on a Cmd-click
  (636, owner: "yes cmd-click" — the engine's own gesture; Ctrl-clicks and every other modified press are
  dropped) and never from the frame: its `window.open` posts `link` to the page, which opens it only when
  `safeLink` allows it (http/https, no login in it, never a loopback or the page's own host — the browser
  bridge's rule; a refusal is said in the sandbox's status slot) in a `noopener` tab — the page keeps the real
  `window.open` for that alone. A link under the pointer gets the title "⌘-click to open the link". The engine's paste handler
  never runs (the frame sends the text to the page, which applies our port of Ghostty 1.3.0's paste
  `encode` and the confirm/refuse thresholds, then posts it back), drops refused, focus reports sent
  by the frame (the engine does not), `scrollback` given in BYTES (upstream #140). The browser probe
  (`probes/591-*/browser-terminal.mjs`) proves each, and that the frame cannot
  read a cookie, fetch, open a socket or reach the page; re-run it on any engine bump.
- **The boot view**: an off/failed/booting sandbox's terminal waits (cover with Start),
  follows the daemon's events BEFORE saying so (the page starts the sandbox only once the terminal waits —
  `startWithBootView`), then writes the daemon's steps/progress and — from "VM created" — the `console
  --follow` stream into the pane as inert text (`WebTerminalWire.bootText`: every control character
  removed; 1000 B lines; 1 MiB in all). When it runs: the image's own session is opened (`open-session`,
  when the terminal asked for none), the streams are stopped AND drained, `boot-done` tells the page to
  scroll the screen into the scrollback, and the first SNAPSHOT's full reset is rewritten to a soft
  reset + clear screen (`keepingScrollback`) — the boot log stays above the session. A wake reports
  "woke in N s" (a state `notice`).
- **`console` is a daemon op and a CLI command** (`doz console NAME [--follow]`, D5): the lines so far
  (in-process when no daemon runs), or a stream of `console` events tailing `Sandbox.bootLogURL` across a
  cold boot's recreated log (`BootConsoleTail`). The CLI never prints the guest's control characters.

## A space workspace's file, plan, state and frames

The space view's server side (`Sources/DozableWeb/WebSpace.swift`; the page itself — the vendored editor and its tab — is a
later step). Four payload-less reads, each the workspace (and a run) in the body, strictly decoded, the name by the store's
rule before any call — never a path: the file is always the record's —, CSRF as every POST, answered in-process when no
daemon runs:

| Route | HostOp | Another computer |
|---|---|---|
| `POST /api/v1/workspace-space` `{workspace}` | `workspace-space` (`doz workspace show W --space --json`): `WebSpaceFile {workspace, file, shownPath (~), text, sha256, bytes, canSave, command?}` — never the absolute path | only with `serve.chat` read or write (else 403 `space-remote`); `canSave` false and the `doz workspace edit … --space-file … --if-match …` command instead |

## The workspace drawn

A workspace a space file made is drawn from its file and its live state by the space editor's renderer
(`vendor/space-editor/space-render.js`, "Vendoring by peer commit" above): a thumbnail on Home (the Workspace cell, 128 × 80;
96 × 60 at phone width) and at the top of an unfolded workspace in the sidebar (`ui.nav_thumbnails`, on by default — the
same setting as the sidebar's session pictures), and the hero on its page, between the title row and the tabs.

- **Which**: `workspace-ls` rows carry `space {file, up}` (from the record, the file never opened; workspaces.md, "Space
  files"), so Home and the sidebar know with no request: a row without one gets the plain tile (Lucide `boxes`, "Made
  without a space file"; nothing in the sidebar), and on its page a compact band ("Made without a space file — `doz
  workspace up -f FILE` draws it"). A page with no space workspace never loads the renderer.
- **The data** (`core/space-pictures.js`): one entry per workspace, shared by every picture of it — the file (`POST
  workspace-space`) and the state (`POST workspace-state`), read one at a time per workspace, at most two reads at once, and
  only for a picture ON SCREEN (`watchVisible`). Staleness comes from events only, never a timer that reads:
  `picturesStale()` on `changed` and `host`; `picturesStale({file: true})` on `hello`, an arrival (`routePage`) and the end of
  an operation that changes the file or the run (a save, up, down, a lifecycle verb; any other operation's end marks the
  states); a burst is coalesced in a microtask. An asleep, finished or archived workspace's state is read once more as it turns
  so (the change into it is drawn), then only on a file mark. Cost: at most one state read per visible space workspace per burst, none for a plain one. **Not live:**
  `changed` follows the sandboxes (and an agent's status while a sandbox is live), so a space whose agents all run on this
  Mac changes on screen at the next hello, arrival, operation end or sandbox change — a `doz workspace down` in a terminal
  is no event of its own (the backlog's `workspaces` topic on `changed`).
- **Drawing**: one render per animation frame, the hero first, then the thumbnails top to bottom. A thumbnail is an `<img>`
  of `render()`'s markup as a `data:` URL (the CSP's `img-src 'self' data:`; one drawing at 160 × 100, `detail: 'thumb'`, for
  Home and the sidebar); the hero (1200 × 500, 800 × 560 at ≤ 760 px — a media listener, never on resize) and the full-window
  view (the window's size) are elements from `renderElement` (no parser, no innerHTML). The theme is always passed (the
  dashboard's `data-theme`, else `prefers-color-scheme` — never `'auto'`: an `<img>` SVG does not follow the page); one
  MutationObserver and one media listener draw the pictures on screen again. `idPrefix` `dzh-NAME-` (hero), `dzf-NAME-`
  (full window), `dzt-NAME-` (thumbs). An LRU of 48 drawings keyed `fileSha|stateSha|detail|w×h|theme` (and the state's
  `observedAt` when one of its Asks can expire — the drawing depends on it), so switching a theme back, or Home's full
  redraw (the same `<img>` moved — a slot per place and name), is a cache hit. The hero is redrawn only when its key
  changes (`data-pic-key`, which the walk reads). The renderer loads the first time a picture shows; a failed load shows
  "The picture could not be drawn". About 20–30 ms a drawing in the walk (a hero ~20, a thumbnail ~30).
- **The hero** (`components/space-picture.js`, `.ws-hero-band`): folds like the brief (`doz.ws.hero:W`; folded on a room's
  address); a button that opens the full-window view (`.sp-full`, no address of its own — Escape, Close or the backdrop
  close it, the focus goes back to the hero). A still: its `live-pulse` stopped (`.ws-hero .live-pulse { animation: none
  !important }` — the drawing's own style is unlayered, so a layered rule needs `!important`); the drawing's own
  `prefers-reduced-motion` rule covers the rest. While an unfolded hero is on screen it sets `body.ws-hero-on`, and the
  notification cards stack at the bottom right instead of hanging over its drawing (the walk checks the boxes never meet). A file that doesn't read (the root `<svg>` has class `problem`): the hero
  adds Dozable's verdict — `workspace-space-plan` once per file sha, the first two problems and the count, and `doz workspace
  up -f FILE --dry-run`; a thumbnail shows only the marker. State unreadable: the file alone.
- **Another computer**: the file follows `serve.chat` through its own route (403 `space-remote` → the tile, "Shown to another
  computer only with serve.chat read"); the state follows the `serve.mac_sessions` projection the server sets. The page
  never sends a viewer field.
- **The walk** (`make dashboard-walk`, "pictures" rows): the first load fetches no renderer byte (the first-load bytes printed,
  the two glue modules ≤ 16 KB), a CSP listener from every document's start counts no violation; `spc2` (a fenced worker on the
  FAKE claude) — a thumbnail per space workspace on Home and in the unfolded sidebar, a tile for each plain one, the renderer
  fetched once, the hero named; 3 s without an event reads no state; the full-window view opens and closes; dark is a new
  drawing, light again a cache hit; under reduced motion no animation; down, then a sandbox change → a new state sha; at
  390 px it fits; a file that doesn't read → the marker and the problem line; the leak sweep; pictures to `SHOTS`.
